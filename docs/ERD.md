# SplitMate — Entity Relationship Design

## 1. Database

Database:

**PostgreSQL**

Primary key strategy:

- UUID
- generated by application or PostgreSQL

Money:

- use `NUMERIC(14,2)`
- never use floating point for financial values

Timestamps:

- `TIMESTAMPTZ`

---

# 2. Entities

## users

Stores application users.

```text
users
-----
id UUID PK
name VARCHAR(100)
email VARCHAR(255) UNIQUE
password_hash TEXT NULL
avatar_url TEXT NULL
created_at TIMESTAMPTZ
updated_at TIMESTAMPTZ
```

`password_hash` can be nullable because OAuth users may not have a local password.

---

## oauth_accounts

Stores external authentication providers.

```text
oauth_accounts
--------------
id UUID PK
user_id UUID FK → users.id
provider VARCHAR(50)
provider_account_id VARCHAR(255)
created_at TIMESTAMPTZ

UNIQUE(provider, provider_account_id)
```

This allows:

```text
Google
Facebook
Apple
```

to be added without adding columns such as:

```text
google_id
facebook_id
apple_id
```

to the users table.

---

## groups

Represents an expense-sharing group.

```text
groups
------
id UUID PK
name VARCHAR(100)
description TEXT NULL
currency CHAR(3)
created_by UUID FK → users.id
created_at TIMESTAMPTZ
updated_at TIMESTAMPTZ
```

---

## group_members

Many-to-many relationship between users and groups.

```text
group_members
-------------
id UUID PK
group_id UUID FK → groups.id
user_id UUID FK → users.id
role VARCHAR(20)
joined_at TIMESTAMPTZ

UNIQUE(group_id, user_id)
```

Roles:

```text
admin
member
```

---

## group_invitations

Stores invitations.

```text
group_invitations
-----------------
id UUID PK
group_id UUID FK → groups.id
email VARCHAR(255)
invited_by UUID FK → users.id
token_hash TEXT
status VARCHAR(20)
expires_at TIMESTAMPTZ
created_at TIMESTAMPTZ
```

Statuses:

```text
pending
accepted
expired
cancelled
```

Do not store raw invitation tokens if avoidable. Store a hash.

---

## expenses

Represents the expense itself.

```text
expenses
--------
id UUID PK
group_id UUID FK → groups.id
description VARCHAR(255)
amount NUMERIC(14,2)
currency CHAR(3)
paid_by UUID FK → users.id
category VARCHAR(50)
expense_date TIMESTAMPTZ
note TEXT NULL
created_by UUID FK → users.id
created_at TIMESTAMPTZ
updated_at TIMESTAMPTZ
```

---

## expense_splits

Defines how an expense is distributed.

```text
expense_splits
--------------
id UUID PK
expense_id UUID FK → expenses.id
user_id UUID FK → users.id
amount NUMERIC(14,2)
created_at TIMESTAMPTZ

UNIQUE(expense_id, user_id)
```

Example:

```text
Expense = Rp600.000

Arifin = Rp200.000
Budi   = Rp200.000
Citra  = Rp200.000
```

---

## settlements

Represents repayments.

```text
settlements
-----------
id UUID PK
group_id UUID FK → groups.id
payer_id UUID FK → users.id
receiver_id UUID FK → users.id
amount NUMERIC(14,2)
settled_at TIMESTAMPTZ
created_at TIMESTAMPTZ
```

Constraint:

```text
payer_id != receiver_id
amount > 0
```

# 3. Relationships

```text
users
  │
  ├──< oauth_accounts
  │
  ├──< group_members >── groups
  │                         │
  │                         ├──< expenses
  │                         │       │
  │                         │       └──< expense_splits >── users
  │                         │
  │                         ├──< settlements
  │                         │
  │                         └──< group_invitations
  │
  └──< settlements
```

---

# 4. Important Constraints

## Expense

```text
expense.amount > 0
```

## Expense Split

```text
SUM(expense_splits.amount) = expenses.amount
```

This must be validated server-side.

## Group Membership

A user must belong to the group before they can:

- create an expense
- view expenses
- view balances
- create a settlement

## Settlement

```text
payer_id != receiver_id
amount > 0
```

# 5. Recommended Indexes

```sql
CREATE INDEX idx_group_members_user_id
ON group_members(user_id);

CREATE INDEX idx_group_members_group_id
ON group_members(group_id);

CREATE INDEX idx_expenses_group_id
ON expenses(group_id);

CREATE INDEX idx_expenses_paid_by
ON expenses(paid_by);

CREATE INDEX idx_expenses_date
ON expenses(expense_date);

CREATE INDEX idx_expense_splits_expense_id
ON expense_splits(expense_id);

CREATE INDEX idx_expense_splits_user_id
ON expense_splits(user_id);

CREATE INDEX idx_settlements_group_id
ON settlements(group_id);
```

---

# 6. Important Design Decision

Do NOT store a permanent `balance` column in the database during MVP.

Balance should be derived from:

```text
expenses
+
expense_splits
+
settlements
```

This avoids synchronization problems.

The backend can calculate:

```text
balance =
payments made
- personal shares
+ settlements paid
- settlements received
```

A cached balance table can be introduced later if profiling proves it necessary.

---

# 7. Transaction Boundaries

Creating an expense must be atomic.

```text
BEGIN

insert expense
insert expense_splits
validate split total

COMMIT
```

If any operation fails:

```text
ROLLBACK
```

The same principle applies to settlements.
